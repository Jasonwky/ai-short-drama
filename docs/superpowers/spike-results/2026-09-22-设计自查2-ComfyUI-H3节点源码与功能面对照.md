## 一、结论先说

1. ✅ **闸门 0-4 成立**。ComfyUI 的 `MiniMaxH3ReferenceToVideo` **确有 `ref_audios` 独立参考音频槽位(max=3)**。
   我上一轮说「证据来自云 API,ComfyUI 路径未核实」——**现在核实了,两条路径一致**。
2. ✅ **参考素材上限完全一致**:图 9 / 视频 3 / 音频 3(另有 3 个"参考视频配套音轨"槽位)。
3. 🔴 **漏了一个决定成败的参数 `ref_image_size`**:`match` vs `max`。官方原文说 `max` 用 2048px 短边
   **identity fidelity 最好**,但「reference tokens ride through every sampling step,
   **so 'max' can be several times slower**」。**这是角色一致性与速度的直接权衡,我设计里没有。**
4. 🔴 **8–15 秒的段落时长不是行业惯例,是模型训练区间决定的**:
   `length` 的 tooltip 原文「**trained range is ~124-362**, longer is untested」
   → 124 帧 ≈ 5.2 秒,362 帧 ≈ **15.1 秒**。**行业收敛到 8–15 秒是被 H3 这类模型的训练区间逼出来的。**
5. 🔴 **`<Picture i>` 标签没有任何校验** —— 节点直接 `clip.tokenize(prompt, minimax_ref_items=ref_items)`,
   写错编号会**静默错位**,不报错。**校验必须我们自己做。**
6. 🔴 **v1 范围漏了四块**,其中 **角色级音色绑定** 和 **跨剧素材库** 是真缺口(见 §四)。
7. ✅ **图片生成不是瓶颈**:4 步 Lightning LoRA 在 4090 上约 **14 秒/张**,全步 40 步约 **5 分钟/张**。
   单集约 25–35 张 → **6 分钟 ~ 2.9 小时**,远小于视频的 8–11 小时。

## 二、ComfyUI H3 节点的真实能力(官方源码)

### 2.1 节点清单

| 节点 | 作用 |
|---|---|
| `EmptyMiniMaxH3LatentAV` | 空的视频+音频联合 latent |
| `MiniMaxH3ImageToVideo` | **`first_frame` / `last_frame`** 皆为 optional 输入 |
| **`MiniMaxH3AddGuide`** | 🔴 **在任意帧锚定**图像/短片/音频/带音轨的短片,**可链式多个** |
| **`MiniMaxH3ReferenceToVideo`** | ref2va 主节点,见下 |
| `MiniMaxH3SigmaShift` | 采样调度参数 |
| **`MiniMaxH3FunControlNetApply`** | 🔴 **ControlNet** —— 姿态/构图控制 |

### 2.2 `MiniMaxH3ReferenceToVideo` 输入(逐条抄自 schema)

| 输入 | 约束 | 备注 |
|---|---|---|
| `clip` | 必填 | |
| `vae` | **optional** | 🔴「Without it reference images/videos **only condition the text encoder**」——**不接 VAE,参考图形同虚设** |
| `audio_vae` | **optional** | 同理,不接则参考音频只作用于文本编码器 |
| `prompt` | multiline | |
| `width` / `height` | default **1344 × 768** | ⚠️ **默认是横屏**,短剧要 768×1344 |
| `length` | default 124, min 5, max 3600, **step 17** | 🔴「trained range is **~124-362**, longer is untested」 |
| **`ref_image_size`** | `match` / `max`,default `match` | 🔴 见 §三.1 |
| `ref_images` | Autogrow, **max = 9** | `ref_image_0…` |
| `ref_videos` | Autogrow, **max = 3** | 24fps,2–15s |
| `ref_video_audios` | Autogrow, **max = 3** | 同编号参考视频的音轨 |
| **`ref_audios`** | Autogrow, **max = 3** | ✅ **独立参考音频 —— 闸门 0-4 的依据** |

### 2.3 引用标签的排列规则(原文)

> References enter the presentation in **fixed order: images, then videos**
> (each soundtrack's `<Audio j>` label **right before** its `<Video k>`),
> **then standalone audio**. Ordinals are **1-based per type**.

即提示词里用 `<Picture i>` / `<Video k>` / `<Audio j>`,**每种类型各自从 1 开始编号**。

### 2.4 帧数规则(与实现对齐)

- 24 fps,帧数吸附到 **17k + 5** 网格(`step=17`)
- 合法片长:5, 22, 39, …, 124, …, 362
- 音频 latent 为 40 fps(`AUDIO_LATENT_FPS = 40`),与视频共享同一时间轴

## 三、🔴 我漏掉的关键设计点

### 3.1 `ref_image_size`:一致性 vs 速度的主开关

官方 tooltip 原文:

> 'match' scales each ref (down only, keeping aspect) to the generation's pixel area;
> **'max' uses the reference pipeline's 2048px short edge for best identity fidelity.**
> Reference tokens ride through every sampling step, **so 'max' can be several times slower.**

> **这是本项目最重要的一个参数**,我的设计里完全没提。
> 角色一致性(identity fidelity)恰恰是本项目的命门,而它直接对应这个开关;
> 但代价是**可能慢几倍** —— 在 36 分钟/条的基础上再乘几倍,是不可接受的。
> **必须实测出 match 与 max 的一致性差距与耗时差距**,才能决定默认档。
> **加入闸门 0 作为必测项。**

### 3.2 段落时长的上限是**模型给的**,不是行业惯例

`trained range ~124–362 帧` = **5.2–15.1 秒**。

> 这解释了为什么 huobao 定 8–15 秒、Toonflow 定 ≤15 秒:
> **不是他们商量好的,是 H3 这类模型的训练区间把所有人逼到同一个区间。**
> 我的设计写了 `段落时长 ∈ [8,15] 秒` 是对的,但**理由写错了**——
> 应该写成「受视频模型训练区间约束,由后端 `Capability` 声明,不是写死的业务规则」。
> 换模型时这个区间要跟着变。

### 3.3 标签校验必须自己做

节点实现是 `clip.tokenize(prompt, minimax_ref_items=ref_items)` —— **零校验**。
提示词写 `<Picture 3>` 但只接了 2 张图,**不报错,静默错位**。

> 我的设计提到了 `@角色名 → 序号` 的映射,但没说要**双向校验**:
> ①提示词里每个标签都有对应素材 ②每个接入的素材都被提示词引用过。
> **两条都要断言,任一不满足 readiness 不通过。**

### 3.4 `MiniMaxH3AddGuide` 比首尾帧更强

可在**任意帧索引**锚定图像/短片/音频,`frame_idx` 负值从末尾计,**可链式多个节点锚多个帧**。

> 我的 `reference_mode` 只设计了 first/last/key 几档。
> 实际上「在第 N 帧锚定」是更一般的形式 —— **子镜头切镜点正好可以用它锚**:
> 一个 12 秒段落含 3 个子镜头,就在 0/96/192 帧各锚一张图。
> **这可能是"段落内多子镜头"最正确的实现方式**,而不是靠提示词描述让模型自己切。
> 🟡 未验证,列入闸门 0 的附加观察项。

### 3.5 `MiniMaxH3FunControlNetApply` —— 站位控制可能有更硬的办法

有 ControlNet 节点。若支持姿态/深度控制,**「空间合同」就不必只靠文字描述**,
可以直接给构图约束。🟡 未细读实现,列为后续调研。

### 3.6 默认分辨率是横屏

`width=1344, height=768`。短剧是 **9:16 竖屏**,要 768×1344。
⚠️ **未验证竖屏是否在训练分布内** —— H3 的训练素材若以横屏为主,竖屏质量可能下降。
**加入闸门 0:竖屏出片质量是否可接受。**

## 四、🔴 v1 范围漏掉的功能(对照 LocalMiniDrama 路由面)

LocalMiniDrama 的路由清单暴露了四块我没考虑的:

### 4.1 🔴 角色级音色绑定(音色一致性的工程做法)

```
POST /characters/:id/sd2-voice-upload     上传角色音色
POST /characters/:id/sd2-voice-refresh    刷新
POST /characters/:id/sd2-certify          角色认证(对接火山方舟资产组)
```

> **这直接印证了闸门 0-4 的方向**:音色不是"希望模型天然一致",
> 而是**把音色作为角色资产的一个字段存起来,每次生成都喂进去**。
> 与「角色三视图」完全同构 —— **角色 = 形象 + 音色**。
> **我的 `character` 表漏了音色字段。**

### 4.2 🔴 跨剧素材库(比剧级资产更上一层)

```
/character-library   /prop-library   /scene-library
POST /characters/:id/add-to-library
POST /characters/:id/image-from-library
```

> 我的设计只做到**剧级**资产复用。他们还有一层**跨剧的全局库**:
> 一个角色做好了可以存进库,下一部剧直接取用。
> 对**商用**平台来说这层价值很高(资产沉淀 = 边际成本下降)。
> 🟡 **建议 v1 不实现,但数据模型留位**:资产表加 `library_id` 可空外键。

### 4.3 🔴 从图反推描述(已有素材能进来)

```
POST /characters/:id/extract-from-image
POST /extract-description-from-image
POST /characters/:id/extract-anchors
```

> 用户手里有现成人物图/场景图时,能**反推出描述与锚点**再纳入体系。
> 我的设计是单向的(文字 → 图),漏了反向入口。
> 这也是「真人素材留入口」那条的自然落点。

### 4.4 工程导出 / 导入 + 大纲层

```
GET  /dramas/:id/export      POST /dramas/import      POST /dramas/import-novel
GET  /dramas/:id/outline     POST /episodes/:id/finalize
```

- **工程 ZIP 导出/导入**:备份、迁移、换机。LocalMiniDrama 的 `EXPORT_VERSION = '1.4'`,
  导出内容含**图片完整历史 + 首尾帧绑定 + frame_prompts + layout_description**。
- **大纲层**:剧本之前还有一层 `outline`(分集大纲),我的设计从"剧本"直接开始,**少一层**。
- **`finalize`(定稿)**:集级定稿动作。

> 另外他们还有 `/characters/:id/generate-four-view-image` —— **四视图不是三视图**。
> 我按 huobao 的 `character turnaround(正/侧/背)`写的三视图,LocalMiniDrama 是四视图。
> Toonflow 截图里「苏万金」也确实是**四张**(正脸/正身/侧身/背身)。
> **应改为四视图**,或做成可配置。

## 五、图片模型速度(闸门 0-1 判据的依据)

| 档位 | 4090 单张耗时 | 出处 |
|---|---|---|
| Lightning **4 步** LoRA | **≈14 秒** | 二手评测(D 级) |
| 全步 **40 步** | **≈5 分钟** | 同上 |

单集图片需求估算:角色四视图(N 角色)+ 场景空镜(M 场景)+ 道具白底(K 道具)+ 每段首帧(13–16)
≈ **25–35 张**。

| | 单集图片总耗时 |
|---|---|
| 4 步档 | **6–8 分钟** |
| 40 步档 | **2.1–2.9 小时** |

> ✅ **图片不是瓶颈**,视频才是(8–11 小时)。
> 所以**图片这一环应该优先画质不优先速度** —— 但要实测 4 步档掉画质多少。
> 我原先那个「单张 ≤3 分钟」的判据是拍脑袋定的,**改为:4 步档 ≤30 秒、全步档 ≤6 分钟**,
> 且两档都要出样张对比。
