- **日期**:2026-09-22
- **触发**:用户「你再详细调研下 huobao 跟其他的 AI 短剧工作流,看看你上面的内容是否正确,是否有漏洞」
- **对象**:`huobao-drama`(CC BY-NC-SA,读码参考)· `Jellyfish`(Apache-2.0)· `LocalMiniDrama`(MIT)
- **方法**:把设计第二节的每条论断拿回源码里找证据。**只记机制,不搬代码。**
- **证据等级**:A(源码原文,本机 grep 可复核)

---

## 一、结论先说

1. **3 条说错了**,都是同一类错误:**把"schema 里有这个字段"当成了"这个机制已实现"**。
2. **8 处漏掉**,其中 4 条是真正有价值的机制,本项目应该补上。
3. **1 条过早悲观**:H3 的 API 支持 `audio_url` **参考音频**,音色一致性可能有解,不必先假设要自建 TTS 链路。
4. **失效传播确实没人做过** —— 但不做是有道理的,他们的生成是云 API 分钟级,我们是 36 分钟/条,**代价差两个数量级**。对我们值得,对他们不值得。

## 二、🔴 我说错的三处

### 错误 1:`characters.seed_value` 是**死字段**

| 我的原话 | 「角色带固定种子,保证重生成时形象不漂」,列为值得抄的机制 |
|---|---|
| **实际** | 全仓 grep `seedValue` **只有 1 处命中:`db/schema.ts:58` 的字段定义本身**。前端、后端、Agent 工具**从未读过它** |
| 性质 | 有字段、没接线。他们**没有实现**角色级种子锁定 |

代码里其他 `seed` 的命中全部是**视频生成任务的种子**(从请求体传入,见 `routes/tasks.ts:52`),
与角色无关。

> **更正**:角色级固定种子这个**想法**仍然有价值(LocalMiniDrama 的 `video_generations` 表里
> seed 是真用的),但**不能说是从 huobao 学来的机制**。我们要做就是我们自己的设计决定。

### 错误 2:huobao 的「首尾帧衔接」**不存在**

| 我的原话 | 「`first_frame_image`/`last_frame_image` 是 schema 里的一等字段,首尾帧衔接不是后期补的功能」 |
|---|---|
| **实际** | 这两个字段全仓只在 `generation.ts:445-446` 出现:按 `params.frameType` 把生成结果写回对应字段。**没有任何代码把上一段的尾帧取出来给下一段当首帧** |
| 性质 | 只是两个存图的字段,不是衔接机制 |

**真正实现它的是 LocalMiniDrama**,而且做法比我设想的好,见 §四.4。

### 错误 3:那几条可量化规则在 huobao 里**没有代码校验**

| 我的原话 | 暗示这套规则是从他们学的,「写成代码断言」 |
|---|---|
| **实际** | `÷500字/分钟`、`÷4.5字/秒`、`÷12秒`、`8-15秒` **全部只存在于提示词文本**(`agents/index.ts:96-104`)。`save_storyboards` 的 zod schema 里只有 `duration: z.number().optional()` —— **无 min/max、无台词下限校验、无段落数校验** |
| 更糟 | `duration: sb.duration || 10` —— **LLM 没给时长就静默填 10 秒**。正是 CLAUDE.md LLM 纪律明令禁止的「默认值填空」 |

> **更正**:规则本身是从他们的提示词里学的(有价值);
> **但"写成代码断言"是我们的改进,不是他们的做法**。他们把这些全交给 LLM 自觉。
> 这条反而是我们相对他们的真实优势,应该明确保留。

## 四、🔴 我漏掉的(按价值排序)

### 4.1 参考模式应该是**每镜可选**,不是写死「首帧图」

Jellyfish `shot_video_readiness.py` 的 `REQUIRED_FRAMES_BY_MODE`:

```
first · last · key · first_last · first_last_key · text_only
```

**六种模式**,`text_only` 不需要任何参考帧。

> 我的设计把「第 5 环 = 首帧图」写死了。实际上转场、空镜、纯环境段落可能
> **根本不需要参考帧**,强制出图是白烧时间。
> **改法**:`segment.reference_mode` 字段,readiness 按模式判定缺哪些帧。

### 4.2 「空间合同」—— 首尾帧强制一致的具体做法

LocalMiniDrama 有个字段 `layout_description`,注释原文:

> 「画面布局与人物站位(**首尾帧模式空间合同**)」
> 「画面布局与人物站位合同(**首尾帧强制一致核心**)」

**首帧和尾帧共享同一份布局描述**,强制两端的构图与站位一致。
另外它的提示词上下文里带 `NEIGHBOR_PREV(上一镜:用于入戏衔接、情绪与空间连贯)`。

> 这正是调研里天工短剧工作台说的「全局站位规划」「下一镜构图参考上一镜」的**开源实现**。
> 我的设计里**完全没有这个概念**。
> **改法**:`segment.layout`(空间合同)字段,首帧/尾帧提示词共用;
> 生成提示词时带上一镜的上下文。

### 4.3 尾帧衔接的正确做法是**从视频里抽帧**,不是生成尾帧图

LocalMiniDrama `tailFrameLinkService.js` 的实际流程:

```
取当前分镜最新 completed 的视频(本地文件)
  → ffmpeg 提取最后一帧
  → 找 storyboard_number 更大的下一个分镜
  → 设为它的首帧
```

> 我原本想的是「生成一张尾帧图」。**从真实视频产物抽帧更对** ——
> 保证的是物理连续,不是"看起来像"。
> 注意它也做了**前置校验**:没有可用本地视频、没有下一个分镜、ffmpeg 不可用,
> 三种情况各给一条可操作的中文错误。

### 4.4 提示词与参考图的**绑定语法**

huobao 的做法(前端 `episode.vue:3186-3199`):

```
人写/Agent 生成: "@林小雨 推开 @老宅大门"
      ↓  按该镜绑定资产的顺序建立 名字→序号 映射
生成时自动替换: "@图片1林小雨 推开 @图片2老宅大门"
```

外加 **`video_prompt` 第一行是信息头**:列出该分镜出场的人物与场景。

> 与 ai-ecommerce 的 `<Picture N>` 同源,但**保留名字**,人读得懂、机器也定位得到。
> 我的设计里**没有定义提示词怎么引用参考图** —— 这是个实打实的缺口,
> 因为「模型不会自己知道哪张图管什么」。

### 4.5 readiness 必须包含**外部依赖**,且每条要给**人话**

Jellyfish 的 check 清单(每条带 `key` + `ok` + `message`):

| key | 检查什么 |
|---|---|
| `reference_frames_ready` | 按参考模式缺哪些帧 →「缺少参考帧:first, last」 |
| `video_model_ready` | 默认视频模型配了吗 / 存在吗 / **是视频类别吗** |
| `provider_ready` | 供应商存在吗 / **有 api_key 吗** |
| `duration_ready` | 时长有吗 |
| `extraction_ready` | 还有 pending 的候选项吗 |
| `prompt_ready` | 提示词有吗 |

> 我只考虑了**内容就绪**(资产绑定齐、提示词齐)。
> **模型/供应商/密钥没配好也是"没准备好"** —— 而且是最常见的那种。
> 而且 readiness 的产物应该是**一串带人话的检查项**,不是一个布尔值。

### 4.6 🟢 H3 支持 `audio_url` 参考音频 —— 音色一致性可能有解

huobao 的 H3 适配器构造的 `content` 数组:

```
{type:'text',      text: prompt}
{type:'image_url', url, role:'first_frame'}     ← 首帧是一等参数
{type:'image_url', url, role:'last_frame'}      ← 尾帧是一等参数
{type:'image_url', url, role:'reference_image'} × N
{type:'video_url', url, role:'reference_video'} × N
{type:'audio_url', url}                          ← 🟢 参考音频
```

> **更正我先前的悲观判断**。我说过「H3 音色跨段落是否一致完全没人验证,不一致就得自建
> TTS + 对口型链路,工期翻倍」。现在看到 H3 **原生接受参考音频**,
> 很可能就是用来锁音色的。
> **闸门 0-3 的验法要改**:不是只验「音色一致吗」,而是验
> **「喂同一段参考音频,音色能锁住吗」**。

### 4.7 H3 的硬性上限,设计里要有校验

| 项 | 上限 |
|---|---|
| 参考图片 | **9** |
| 参考视频 | **3** |
| 参考音频 | **3** |
| 混合总数 | **12** |
| 提示词 | **7000 字符** |
| 画幅 | `16:9 / 9:16 / 1:1 / 4:3 / 3:4 / 21:9` |
| 有首帧时 | `ratio` 恒为 adaptive,**必须省略**;无首帧时必填 |

⚠️ **注意适用范围**:以上是 **MiniMax 云 API** 的限制。
我们走的是**云机 ComfyUI + 开源 H3 权重**,节点是 `MiniMaxH3ReferenceToVideo`,
参考图走 `ref_image_0…` 的 Autogrow 槽位 + 提示词里 `<Picture N>` 标签。
**两条路径的参数形态不同,上限是否一致未核实** —— 列为闸门 0 的待测项。

### 4.8 字幕与配音:huobao **根本没实现**

| 项 | 实际 |
|---|---|
| `subtitle_url` | schema 里有字段,**全仓零处代码使用** |
| TTS / 配音 / 音色 | grep `tts\|voice\|配音\|音色\|dubbing` → **零命中** |
| README 宣称 | 「FFmpeg per-shot compositing and **subtitle handling**」 |

> 🔴 **README 与代码不符**。字幕这一环**不能假设照抄就行**,得自己做。
> 配音则是完全依赖视频模型原生音频 —— 这也侧面印证了 §4.6 的路线。

## 五、关于失效传播:确认**没人做过**

grep `invalidat|stale|outdated|失效|过期|dirty` across huobao 前后端:
唯一相关的一处是 `extract-tools.ts:385`「物品外貌变更后旧的最终提示词失效」
—— 只是把 `final_prompt` 置空,**不波及已生成的图与视频**。

改角色图**不会**把下游分镜图/视频标记为过时。
他们筛「未生成项」靠的是 **`image_url` 是否为空**,而不是状态机。

> **这不代表我的设计错,但论证要诚实**:
> 他们单条生成走云 API(Seedance mini 一条几十秒到几分钟),重跑成本低,
> 「不知道哪些过时了」的代价可以忍。
> **我们是 36.4 分钟/条、8–11 小时/集,代价差两个数量级。**
> 所以失效传播对我们值得做,对他们不值得。**这是场景差异,不是他们疏漏。**

## 六、一个反面教材:huobao 自己的任务系统是**混合的**

| 任务类型 | 存在哪 |
|---|---|
| 图片/视频生成 | `sys_task` **落库** |
| 批量视频提示词 | `const tasks = new Map()` **进程内内存态** |

`video-prompts.ts` 文件头注释原文:
> 「进程内内存态:按集跟踪一份任务,运行中不重复启动;**重启后状态丢失**」

> 他们自己知道这是个妥协。
> **我们的设计说「统一任务表」是对的,而且这一点上比他们强** ——
> 前提是**所有**长任务都进同一张表,不给自己留内存态的口子。
