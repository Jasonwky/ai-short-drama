# 开源图片模型选型(云机 ComfyUI,4090 24GB)

- **日期**:2026-09-22(所有事实于此日查证)
- **动机**:用户定了「图片这一环跑在云机 ComfyUI,哪个开源模型效果好用哪个」。
  MiniMax H3 只出视频不出图,而**参考图是整条一致性链路的地基**,必须自己解决。
- **硬性要求**:①开源可商用(读 LICENSE 原文)②支持**多图参考/角色一致性**
  ③4090 24GB 能跑 ④ComfyUI 原生支持
- **状态**:🟡 **选型建议已出,但未实机验证**。实测需要开云机,见 §六。

---

## 一、结论先说

1. **首选 `Qwen-Image-Edit-2511`(Apache-2.0)**。它同时满足四条硬性要求,
   且有一条别人没有的能力:**从单张参考图生成多视角**,直接对应「角色三视图」这个刚需。
2. **配 `Multiple-Angles LoRA`**(fal 版 1549 likes)专门做多视角,240MB,即插即用。
3. **量化档选 fp8mixed(20.53 GB)或 GGUF**。bf16 是 40.86 GB,4090 装不下。
4. 🔴 **图模型与 H3 在同一张 4090 上放不下** —— H3 已实测 23/23GB 满载,
   图模型 fp8 还要 20.5GB。**必须换入换出,不能并行。**
   这不是调参问题,是架构约束,见 §五。
5. **排除项**:FLUX.1 [dev]/[Kontext dev] 非商用;HunyuanImage-3.0 有**地域限制**且 80B 太大;
   FLUX.1 [schnell] 虽 Apache-2.0 但无多图参考能力,做不了角色一致性。

## 三、为什么是 Qwen-Image-Edit-2511

### 1. 多图参考 + 角色一致性是它的主打能力

2511 版(2025-12-26 发布)相对 2509 的改进就是:**提升角色一致性、减少多轮编辑漂移、
一次接受最多 3 张参考图**。这正好对上本项目的用法:
角色三视图 + 场景空镜 + 道具白底图,合成一张分镜首帧。

### 2. 单图转多视角 —— 直接解决"角色三视图"

2511 的能力清单里有「**multi-angle view generation from a single reference image**」。
配合专门的 LoRA 效果更稳:

| LoRA | 出处 | 体积 |
|---|---|---|
| `fal/Qwen-Image-Edit-2511-Multiple-Angles-LoRA` | fal,**1549 likes** | ~240MB |
| `dx8152/Qwen-Edit-2509-Multiple-angles` | 981 likes,2509 版 | ~240MB |

Comfy-Org 的官方打包里也带了 `Qwen-Edit-2509-Multiple-angles.safetensors`。

### 3. ComfyUI 原生支持,有官方教程

`docs.comfy.org/tutorials/image/qwen/qwen-image-edit-2511` 给了原生工作流,四个模型文件:

| 文件 | 说明 |
|---|---|
| `qwen_image_edit_2511_bf16.safetensors` | 扩散模型,**40.86 GB** |
| `qwen_2.5_vl_7b_fp8_scaled.safetensors` | 文本编码器(Qwen2.5-VL 7B) |
| `qwen_image_vae.safetensors` | VAE |
| `Qwen-Image-Edit-2511-Lightning-4steps-V1.0-bf16.safetensors` | 可选,**4 步加速 LoRA** |

### 4. 中文渲染能力强

Qwen-Image 系列把语言与版面推理做进了架构,中英文字都能稳定嵌进画面。
短剧要烧字幕、要出招牌/信件/手机屏这类画面内文字时,这条是实打实的优势。

## 四、量化档与显存

Comfy-Org 打包仓(`Comfy-Org/Qwen-Image-Edit_ComfyUI`)里的实际体积:

| 档位 | 体积 | 4090 24GB |
|---|---|---|
| `qwen_image_edit_2511_bf16` | **40.86 GB** | ❌ 装不下 |
| `qwen_image_edit_2511_fp8mixed` | **20.53 GB** | ⚠️ 勉强,加 7B 文本编码器就超 |
| `qwen_image_edit_2511_int8_convrot` | **20.50 GB** | ⚠️ 同上 |
| GGUF(`unsloth/Qwen-Image-Edit-2511-GGUF`,30 天 **39.7 万次**下载) | Q4/Q5 更小 | 🟢 **显存最舒服的一档** |

⚠️ **算一笔显存账**:fp8 扩散 20.5GB + Qwen2.5-VL 7B 文本编码器(fp8 约 8GB)= **28.5GB > 24GB**。
ComfyUI 会自动分步加载/offload,但**会明显变慢**。所以:
- 要么用 **GGUF Q4/Q5** 压到一次装得下
- 要么接受 offload 的耗时代价
- **哪档能跑、多快、画质掉多少,必须实测**,不能靠推算

## 五、🔴 架构约束:图和视频不能共存于同一张卡

| 模型 | 显存占用 | 出处 |
|---|---|---|
| MiniMax H3 (ref2va, pruned_fp8) | **23 / 23 GB 满载** | ai-ecommerce 云机 4090 **实测** |
| Qwen-Image-Edit-2511 fp8 + 文本编码器 | **≈28.5 GB** | 按文件体积推算 |

**结论:一张 4090 上,图模型和视频模型必须换入换出,不能并行。**

这不是优化问题,是设计前提。它直接推出两条:

1. **流水线必须分阶段跑,不能逐镜"出图→出视频"交替**
   —— 那样每镜都要换一次 20GB 权重,光加载就烧光时间。
   正确做法:**先把整集的图全部出完,再整批出视频。**
2. **任务队列要按"模型"分组调度**,而不是按"分镜"顺序调度。
   同一模型的任务尽量连着跑,把权重换入换出的次数压到最少。

> 这条约束是本次调研最有价值的发现之一 —— 它在写第一行代码之前就决定了队列的调度策略。

## 六、🟡 未验证项(需要开云机实测,这是下一步)

**以下全部是推算,一条都没在真机上跑过**:

| 待测 | 为什么必须测 |
|---|---|
| fp8 / GGUF 哪档能在 4090 上跑起来 | 28.5GB > 24GB,offload 的实际代价未知 |
| 单张图耗时 | 产能账里图片这块目前是空白 |
| 多视角 LoRA 的三视图效果 | 一致性的地基,效果不行整条链路不成立 |
| 三张参考图合成分镜首帧的效果 | 这是本项目的主用法,官方只说"最多3张",没说效果 |
| 模型换入换出的实际耗时 | 决定 §五 的调度策略值不值 |
| Lightning 4 步 LoRA 掉画质多少 | 决定要不要用 |

**建议的实测顺序**(一条不过就别往下走):
1. 装得下吗 → 2. 三视图出得对吗 → 3. 三图参考合成首帧像不像 → 4. 多快 → 5. 换模型多久

## 七、反证与局限

1. ⚠️ **排行榜不等于适用**。HunyuanImage-3.0 在 Text-to-Image Arena 排国产第一(1151 分),
   但 80B MoE + 地域限制,对本项目**完全不可用**。分数高低与能不能用是两回事。
2. ⚠️ **开源模型的一致性有公认短板**:检索到的评测称
   「Qwen、HiDream 等开源模型在 **3 轮以上编辑后角色漂移概率显著**,
   而 GPT-Image-2 多轮编辑仍能保持一致」。—— 这意味着**多轮反复改同一张图是危险操作**,
   应该改成「从原始三视图重新合成」而不是「在上一版基础上继续改」。
   🔴 这条是 D 级证据(二手评测,未见方法论),但方向性足够引起警惕,**实测时要专门验这一项**。
3. ⚠️ **FLUX.1-Kontext-dev 的许可证原文没取到**,只有 HF 标签 `other`。
   现阶段按非商用排除,但**这是个未闭合的核实项**。
4. ⚠️ **GLM-Image(MIT)没细查**,可能是漏掉的备选。
5. ⚠️ 本文没有**任何实测数据**,全部来自模型卡、官方文档与文件体积。
