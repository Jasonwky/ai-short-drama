## 一、结论先说

| # | 结论 | 对设计的影响 |
|---|---|---|
| 1 | 🔴 `response_format: json_schema`(Chat)与 `text.format`(Responses API)被**静默忽略**:HTTP 200,输出是 ```json 围栏包着的自由发挥,`prompt_tokens` 显示 schema 根本没送进模型 | 不能用这两种传法;**这是静默降级**,不做实测就会上当 |
| 2 | ✅ 「强制调用一个 strict 工具」时 schema 会送进模型,结构**大体**被遵守 | 客户端只用这一种传法 |
| 3 | 🔴 但 strict **不是服务端约束解码**:实测出现过①工具参数不是合法 JSON(原文半角双引号没转义)②凭空多出 `start_quote_placeholder` 字段 ③默认模型在诱导下照填 enum 外的值 | **客户端必须再校验**(`jsonschema`),不合格退回重做 —— CLAUDE.md 的「用代码闸门」在这里不是多余,是唯一保证 |
| 4 | 🔴 schema 挡不住**内容**越界:诱导它加 `extra_note`,GPT 把内容塞进了台词字符串 | 判卷要「用数据审」:台词逐字对剧本原文、大纲段号首尾相接覆盖全文 |
| 5 | ✅ 默认模型选 **`deepseek-v4-flash-0731-new`**:分镜任务 6/6 通过、每次 2 轮、42–53 秒、约 5.4k token、已知价格最低 | `tools/llm/service.py: DEFAULT_MODEL` |
| 6 | ⚠️ 服务**只有 http**(https 连接被拒):key 与发送的剧本 / 小说原文**明文传输**;数据发往第三方 | 与 CLAUDE.md「离线优先 / 数据不外发」冲突,用户已知情选择;控制台在 LLM 按钮旁写明「会发送给 LLM 服务」 |
| 7 | ⚠️ 「一字不差」要按「全角半角视为同字」判:原文半角逗号,模型照抄时写成全角 | `tools/llm/verbatim.py`(一对一折叠),分镜台词核对用 |
| 8 | 🔴 **别让模型逐字抄长原文**:小说大纲让它抄「起止原句」,会抄错字(「她她他的目光」)、改写、换标点 | 大纲改成**代码给原文分段编号、模型只回起止段号**,代码核对首尾相接后按段切原文 |

## 三、结构化输出三种传法(7 个模型 × 诱导违规的提示词)

提示词故意要求「额外加一个字段 extra_note」「mood 填 nostalgic(不在 enum 里)」。

| 传法 | 结果 |
|---|---|
| Chat `response_format: {type: json_schema, strict: true}` | 7/7 模型输出 ```json 围栏、字段自编、mood=nostalgic、带 extra_note;prompt_tokens 48–60(schema 没进) |
| Responses API `text.format` json_schema | 3/3(抽测 deepseek-pro / terra / astra)同样不是 JSON |
| Chat + `tools`(strict)+ `tool_choice` 强制 | 3/3 结构守住(mood 在 enum、无多余字段);prompt_tokens 122(schema 进了);但 GPT 两款把 extra_note 的内容塞进了台词字符串 |
| Chat `response_format: json_object` | 只保证是 JSON,不管 schema |

## 四、模型选型:真实分镜任务(真实 schema + 真实判卷,最多回炉 3 轮)

**失败 / 回炉原因**(读每轮判卷记录):
- GPT 系列:在「段落数 5 > 4」与「某段子镜头 5–7 个 > 4」之间来回摆 —— 压段数就把台词塞进一段。告诉它范围也没改掉
- DeepSeek 两款:段数、子镜头都守规矩;首轮几乎总是漏写一两个 `@名字`(绑定了场景却没在首帧提示词里 @),一轮反馈就改好

**反证**(为什么不是判卷规则太严):手写的正例(4 段、每段 2–3 个子镜头)能同时满足全部规则(`tests/llm/test_storyboard.py::good_args`);
DeepSeek 6/6 通过也说明这组规则可以同时满足。「告诉它段数」对 DeepSeek 无害、对 GPT 没用,保留(确定性数据)。

**选型理由**:可靠(6/6)> 速度 > 成本。flash 每次约 5.3k token,按已知价约 0.006 元。
**没量的**:内容写得好不好(分镜的画面感、提示词质量)—— 这一关靠控制台审阅页人工批准。

## 五、契约测试(真 LLM,`python -m pytest -m real_llm -q`)

**首跑**:分镜 / 声音 / 梗概剧本 / 对抗测试 4 条过,**小说大纲失败**:模型照抄原句时把半角逗号写成全角 → 加 `verbatim.py`;
回炉时出现非法 JSON、多余字段(第一节 #3)→ 客户端校验兜住;「每集事件 3–6 条」放宽到 2–8 条(下游不依赖,7 条正常事件被打回)。

**稳定性(改之前的设计)**:整套 5 条连跑 2 遍 —— 第 1 遍 2 条失败:①大纲 3 轮都有原句抄错(乱码、改写)②对抗测试:默认模型填了
`mood=nostalgic`(enum 外),**推翻了「strict 守得住结构」这个假设**(第三节里守住的是另外几个模型)。第 2 遍 5/5。另有 2 次大纲在 2 秒内失败、
原因没抓到(pytest 只保留最近 3 个临时目录)→ 契约记录改落仓库 `tmp/contract_llm/`。

**据此改了两处设计**:
1. 大纲不再抄原句,改为**段号**(见第一节 #8)
2. 对抗测试不再断言「strict 守得住」,改为断言「**闸门**把诱导违规纠正过来」—— 这才是我们真正依赖的保证

**改后**:整套 5 条连跑 3 遍:第 1、2 遍 5/5;第 3 遍分镜 1 条 3 轮没收敛(段数 5 ↔ 某段子镜头 8 个来回摆,另有一段 @ 了没绑定的道具 ——
判卷判得对)。分镜是约束最多的任务,轮次上限改为 4(其余任务仍是 3),分镜契约单条再连跑 4 遍:4/4 通过(47–76 秒)。

**结论**:默认模型 + 闸门的组合在黄金样本上可用,但**不是 100%**;分镜在 4 轮上限下近 16 次(测量 6 + 契约 10)只失败过 1 次(那次是 3 轮上限)。
失败时产物落成 failed、带每轮问题,人看得见,不会静默写回。

## 六、改了什么

- `tools/llm/client.py`:只用 strict 工具调用;截断 / 拒答 / 没调工具 / 连不上各自的异常
- `tools/llm/gate.py`:schema 体检 + `jsonschema` 客户端校验 + 代码判卷 + 回炉 + journal
- `tools/llm/verbatim.py`:逐字比对的全角半角折叠
- `tools/llm/storyboard.py`:段数范围写进输入;轮次上限 4(`service.TASKS`)
- `tools/llm/outline.py`:原文分段编号、模型只回段号;事件 2–8 条
- `tools/llm/service.py`:`DEFAULT_MODEL = "deepseek-v4-flash-0731-new"`
