# 多 agent 并行开发复盘(P19-A 原创分集)

- **日期**:2026-10-24
- **起因**:用户要求「开多 agent,提高开发效率」。
- **做法**:主会话先写地基(spec、库结构 v20、三方共用的纯函数)并提交;3 个 agent 各在一个 git worktree 里并行实现
  骨架任务 / 展开任务 / 单集变体加强,只许动各自的文件;主会话逐个合并、每次跑全量;共用文件(任务登记、审阅页、大纲页、假样例、自测)
  合并后由主会话串行改;最后另派一个 agent 不带结论地独立复查整体 diff。
  依据 CLAUDE.md M-21「写操作保持单线程」:并行写在隔离的 worktree 里,往主线落盘是单线程的。

## 结论先说

1. **能并行、没冲突**:三个分支按文件边界切开,合并零冲突,每次合并后全量绿(1001 → 1017 → 1033)。
2. **🔴 worktree 不是从本地最新提交建的,而是从远程 `origin/HEAD`(当时 `904bf5b`)建的**。本地 main 当时领先远程 37 个提交(没推送),
   三个 agent 开工时都看不到地基;三个都自己发现并 `git merge --ff-only main` 才开始。**这是靠 agent 自觉兜住的,不是机制保证的**。
   → 以后派 worktree agent 前先推送,或在任务说明里写明「先 `git merge --ff-only main`,确认 `tools/llm/skeleton.py` 存在再动手」。
3. **接口约定写进任务说明是关键**:主会话在派活时写死了函数名、签名、返回结构、文件边界;三个 agent 交回的接口都没有偏离,
   合并后只做了一处整理(骨架 agent 为「不动文件头」把导入放在了文件中间,合并后挪回文件头)。
4. **subagent 的提醒有价值,但仍要自己验**:两个 agent 都提醒 schema 里的 `minItems`/`maxItems` 可能不被命令行接受 ——
   主会话跑真 LLM 契约验证:两条都一轮通过,命令行接受。

## 数据(墙钟时间,来自任务通知)

| agent | 内容 | 耗时 | 交回时测试 |
|---|---|---|---|
| 单集变体加强 | 改 1 个模块 + 3 条测试 | 5.3 分钟 | 1001 通过 |
| 展开任务 | 新模块 + 16 条测试 + 契约测试 | 9.0 分钟 | 1014 通过 |
| 骨架任务 | 追加任务 + 16 条测试 + 契约测试 | 9.1 分钟 | 1014 通过 |

- 三个并行,实现阶段墙钟约 9 分钟(取最长的一个)。
- **对照不完整(反证)**:本次没有让同一份工作再用单 agent 串行做一遍,所以「省了多少时间」没有实测对照,只能按三段耗时之和(约 23 分钟)估计串行上限;
  串行时主会话不用写那么细的任务说明、也不用合并,实际差距会比 23 vs 9 小。按 CLAUDE.md「必须自建分工 vs 单 agent 的对照证据」,
  这条记为**未证实**,下次有同等规模、可切分的工作时做一次真对照。
- 额外成本:主会话写三份自包含的任务说明(含接口约定、文件边界、参照文件)、逐个核对 diff 与合并;三份 subagent 共用约 28 万 token。

## 什么时候适合 / 不适合

- 适合:能按**文件**切开、接口能事先写死的独立模块(本次三块各自只动自己的文件);
- 不适合:要改同一批共用文件的工作(任务登记、模板、自测表)—— 这些本次一律留给主会话合并后串行改;
- 需要「先 A 后 B」才能定接口的,先由主会话把地基写好提交,再并行。
